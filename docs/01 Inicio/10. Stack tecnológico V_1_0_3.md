### 1. Metodología de Puntuación Multicriterio

Para la selección del stack tecnológico se utiliza una matriz de ponderación objetiva basada en la siguiente ecuación:

$$\text{Puntuación Final} = \sum_{i=1}^{n} (\text{Valoración Criterio}_i \times \text{Peso}_i)$$

Donde cada criterio se valora en una escala discreta de **1 a 5** (1 = Muy Deficiente, 5 = Excelente) con los siguientes pesos:

* **Costo / Licenciamiento (Código Abierto):** $25\%$
* **Rendimiento / Adecuación a Heurísticas:** $25\%$
* **Compatibilidad Móvil / Funcionamiento 2G/3G:** $20\%$
* **Soporte GIS Espacial:** $15\%$
* **Facilidad de Integración y Curva de Aprendizaje:** $15\%$

### 3. Justificación Técnica Formal del Stack

Se confirma la adopción del stack $100\%$ código abierto, con prioridad en dos dimensiones clave del proyecto: optimización de rutas y operación geoespacial en red móvil limitada.

* **Opción 1 — Python + FastAPI + React + PostgreSQL/PostGIS + Leaflet + Redis/Celery:** Se selecciona como la alternativa optimal para el caso de uso porque combina mejor la capacidad científica de cómputo para algoritmos metaheurísticos con la necesidad de una aplicación web liviana y accesible para conductores en entornos con conectividad variable.
* **Python 3.11 + FastAPI:** Proporciona una API REST asíncrona de alto rendimiento, ideal para ejecutar re-optimización de rutas y procesos pesados en segundo plano con tiempos de respuesta inferiores a 30 segundos.
* **DEAP / OR-Tools:** Son herramientas maduras para resolver VRPTW, rutas con restricciones, zonificación y objetivos de sostenibilidad mediante metaheurísticas o optimización combinatoria.
* **PostgreSQL 15 + PostGIS 3:** Se confirma como la capa persistente geoespacial base del sistema, permitiendo almacenar coordenadas GPS, límites distritales de Lima, polígonos de zonas sensibles y consultas espaciales rápidas.
* **React.js + Tailwind CSS + PWA:** Permite una interfaz responsive, rápida y accesible para el modo conductor, con menor consumo de datos y mejor soporte para dispositivos de gama baja o conectividad inestable.
* **Leaflet.js + OSRM local:** Evita costos recurrentes por API de ruteo, mientras permite un motor de rutas totalmente controlado y adecuado para escenarios urbanos con mapas de OpenStreetMap.
* **Redis + Celery:** Facilita la ejecución asíncrona de tareas pesadas de optimización sin bloquear la interfaz del usuario, soportando re-optimización por cancelaciones, cambios de demanda o eventos de tráfico.

La **Opción 2** resulta atractiva para aplicaciones con alta exigencia de tiempo real, alertas y WebSockets, pero presenta un menor nivel de madurez para la optimización de rutas basada en heurísticas complejas y escenarios de cálculo intensivo. La **Opción 3** es sólida en entornos empresariales y para motores de optimización maduros, sin embargo, incrementa la complejidad operativa y no es la mejor alternativa para un producto con fuerte componente móvil, geoespacial y de despliegue ágil.

En síntesis, el stack recomendado es:

* **Backend:** Python 3.11 + FastAPI
* **Frontend:** React.js + Tailwind CSS + PWA
* **Base de Datos:** PostgreSQL 15 + PostGIS 3
* **Mapeo y Rutas:** Leaflet.js + OSRM local
* **Procesamiento Asíncrono / Caching:** Redis + Celery

Este diseño maximiza el equilibrio entre rendimiento científico, costo, escalabilidad, soporte espacial y capacidad operativa para un sistema de optimización de rutas en contexto urbano peruano.
