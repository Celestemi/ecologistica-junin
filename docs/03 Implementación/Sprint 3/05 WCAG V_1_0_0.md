# Evaluación de Accesibilidad WCAG 2.2 Nivel AA

**Versión documental:** V_1_0_0

**Proyecto:** EcoLogística Junín<br>
**Fecha de evaluación dinámica:** revisión del sprint<br>
**Revisión estática del proyecto actual:** revisión del sprint<br>
**Objetivo:** evaluación puntual del frontend servido en `http://localhost:8080` y contraste de los hallazgos con el código actual<br>
**Norma de referencia:** WCAG 2.2, niveles A y AA  
**Herramientas:** Lighthouse 13.5.0, axe-core 4.14.0 y Playwright 1.64.1 con Google Chrome en modo headless

## Alcance, pantallas y método

### Evaluación vigente — revisión del sprint

Se levantó un stack Docker temporal con PostGIS, backend y frontend en puertos aislados. La base se creó desde cero; se optimizó una ruta únicamente en esa base, se asignó temporalmente el vehículo con ruta al conductor de demostración y se eliminó todo el stack al finalizar. No se modificaron datos locales existentes.

Se usaron Google Chrome headless, Playwright 1.64.1, axe-core 4.14.0 y Lighthouse 13.5.0 instalados temporalmente fuera del árbol del proyecto. Lighthouse se ejecutó con sesión autenticada para operador y conductor. Sus puntuaciones son heurísticas y **no son porcentajes de conformidad WCAG**.

| Flujo | Lighthouse Accessibility | axe-core WCAG A/AA | Interacción automatizada |
|---|---:|---:|---|
| Ingreso | 100 | 0 violaciones / 0 nodos | Carga pública verificada. |
| Seguimiento sin pedido | 100 | 0 violaciones / 0 nodos | Carga pública verificada. |
| Operador con ruta aislada | 100 | 2 tipos / 3 nodos | Vista tabular: 5 botones de parada; Enter seleccionó una parada y mostró detalle. |
| Conductor con ruta aislada | 100 | 0 violaciones / 0 nodos | Diálogo: foco inicial, Tab contenido y Escape con retorno de foco verificados. |

El reflow automatizado comprobó ingreso a 320 CSS px (`scrollWidth=clientWidth=320`) y conductor a 390 CSS px sin desbordamiento horizontal. No se hicieron pruebas visuales a 320 CSS px para todas las pantallas ni zoom 200 %/400 %.

### Evidencia histórica — revisión previa

Los resultados de Lighthouse y axe-core que siguen corresponden a la ejecución de la revisión previa. El revisión del sprint se revisaron las pantallas y componentes del árbol actual (`src/pages`, `src/components` y `src/index.css`) para detectar cambios que hacen obsoletas algunas conclusiones. No se volvió a ejecutar Lighthouse, axe-core ni Playwright sobre la versión actual; por tanto, la revisión de código no se presenta como una nueva medición de conformidad ni confirma cambios visuales en navegador.

Durante la evaluación dinámica anterior, el frontend respondió HTTP 200 y se comprobó el flujo legítimo de autenticación mediante las cuentas de demostración ofrecidas por la propia pantalla. No se inventaron sesiones ni se eludieron controles. Se evaluaron:

- ingreso público;
- seguimiento público sin pedido seleccionado;
- panel autenticado del operador, incluidos mapa de rutas disponible, filtros, navegación, KPIs operativos y ambientales;
- vista del conductor y estados visibles de conexión/sincronización;
- código del detalle por parada y de la vista tabular alternativa.

En la captura dinámica no había una ruta publicada, por lo que no se renderizaron la vista tabular ni el detalle de una parada. No se ejecutó una optimización porque habría alterado datos. En el código actual la tabla es alcanzable por teclado; esa mejora estática aún requiere validación dinámica con datos de prueba aislados.

Lighthouse se ejecutó sobre ingreso y seguimiento. Obtuvo **90** y **95**, respectivamente, en la categoría Accessibility. El intento sobre `/` terminó en el ingreso porque Lighthouse abrió un contexto nuevo sin la sesión de la prueba; ese resultado duplicado (90) no se atribuye al panel. Las cifras de Lighthouse son puntuaciones heurísticas y **no son porcentajes de conformidad WCAG**.

axe-core se ejecutó sobre ingreso, seguimiento, panel autenticado con mapa/KPIs y vista del conductor. La revisión manual asistida incluyó orden de tabulación básico, indicador global de foco, semántica visible, nombres de controles y análisis del código de tabla, detalle, mensajes y diálogo. La inspección estática actual también verificó el `<main>` de ingreso, los atributos `alt` de los marcadores, la activación por teclado de las filas y los anuncios de estado/error presentes en el conductor y seguimiento.

## 6. Mejoras implementadas y evidencia actual (revisión del sprint)

- **1.3.1, 2.1.1 y 4.1.2:** la alternativa tabular se puede seleccionar aun cuando el mapa está disponible. Cada parada se selecciona con un `<button>` nativo, en vez de convertir la fila de tabla en un control artificial; se conserva el detalle de parada y la selección por teclado.
- **2.1.1, 2.4.3, 2.4.7 y 2.4.11:** el diálogo de firma toma el foco al abrirse, contiene Tab/Shift+Tab, permite Escape y devuelve el foco al botón que lo abrió. La foto de comprobante sigue siendo una alternativa completa al canvas, que ahora explica su carácter opcional.
- **1.4.10 y 2.5.8:** los controles añadidos usan objetivos mínimos de 44 px; la tabla conserva desplazamiento horizontal solo para sus columnas, mientras el resto de la página evita desbordamiento horizontal. Los controles de zoom Leaflet tienen ajuste específico para 320 CSS px.
